# Native builds and Internet room codes

## Intent

Two friends should be able to play across Windows, macOS, Linux, and Steam Deck. One hosts a room and shares its code. The other enters it in the game. Once the game is running with a supported ROM, both can do this with the shipped network settings, without creating an account, setting up a VPN, or forwarding a router port. Communities can run the same relay service on their own infrastructure and use it from the official game builds.

Ship native packages on one GitHub release tag and use a public relay for Internet room-code sessions. Include Versus, Dramatic Battle co-op, and the existing spectator role. Keep local play, LAN browsing, direct IPv4 joins, and the optional community directory available. Public Internet room browsing through the relay, skill-based matchmaking, gameplay changes, storefront distribution, and direct Internet path negotiation are outside the first release.

## Approaches

- **Relay all Internet room-code traffic. Selected.** The game connects to a default service that allocates a room code and forwards rollback packets. Players have one connection path to exercise on every platform. That service carries the traffic for every Internet room-code match, so its availability and location affect play.
- **Try direct first, then relay.** The service also exchanges connection candidates. Peers try to reach each other and fall back to the relay when necessary. A successful direct connection can reduce latency and relay traffic. Path selection, timeouts, and fallback add cases to implement and verify. The host-and-code experience can stay the same if this approach is added later. [ICE](https://www.rfc-editor.org/rfc/rfc8445.html)

The maintainer chose relay first, with a low-cost US East default relay and first-release support for community-operated relays. The first Mac build targets Apple silicon. The project currently has no Developer ID or Mac test device. A physical Steam Deck is available.

## Player flow

- **Host.** Opening an Internet room is the default Host Match action. The host picks Versus or Dramatic Battle as today. Show a short, shareable code when the selected relay has created the room. Keep that code valid through character and stage selection, play, rematch, and reselect. Closing the room or losing the host ends the room after a bounded timeout.
- **Join.** Accept the Internet code through the existing join flow, with keyboard entry and native desktop copy and paste where supported. Choose the format so codes cannot be mistaken for the existing address codes. Make manual entry case-insensitive and usable with the Deck's built-in controls in Gaming Mode. A player can join as a challenger, a Dramatic Battle ally, or a spectator. A spectator can use the same code before or during a match.
- **Connection failures.** A player can cancel or retry a pending operation. Report invalid, expired, full, incompatible, and unreachable rooms in the menu where the player can act on the error. After a relay disconnect, return to a usable menu with a clear reason. A new room is sufficient for retry in the first release.
- **Community relay.** In Netplay settings, let players enter a custom relay hostname and optional port, see the relay currently selected, and return to the default. Hosts and guests set the same relay once, then use the normal room-code flow. Codes belong to the selected relay. A failed lookup stays on that relay and the error identifies the relay being used.
- **LAN and direct play.** Keep a local hosting choice and the existing IPv4 and LAN address-code parsing. Relay invite rooms are reachable by code. LAN discovery and the optional HTTP directory continue to serve direct rooms, including when the relay is unavailable.

## Client and relay

Use the typed command and event boundary between `GameSession` and `sf-host`. Give the client transport distinct targets for an Internet room code and a direct address. `sf-host` manages sockets, relay setup, and cleanup off the game loop. Map the relay's participant identities to the local peer routes used by `SendPacket` and `PacketReceived`. A room announcement update must reuse the current room. The existing handshake still checks the build and effective ROM/data and art identities, and the game session still owns player and spectator roles, rollback, confirmed input playback, and rematch. Keep the existing packet payloads and maintain end-to-end peer ping/jitter for input delay. [Netplay ADR](../adr/0018-rollback-netplay-and-virtual-net-bus-on-the-1987-engine.md) · [Transport commands and events](../../crates/sf-engine/src/netplay/transport.rs)

Both clients dial the selected relay outbound. Use authenticated encrypted connections to the relay and a datagram transport that preserves the existing game's tolerance for loss and reordering. QUIC datagrams with a reliable stream for room operations are the starting point for evaluation. Verify that the game's maximum 512-byte packet plus the routing header fits the supported datagram size. Keep game payloads opaque to the forwarding service. Route only between connections in the same room, using identities assigned by the relay and bound to each connection. A room code grants access to attempt a join. Host control stays bound to the host connection. [QUIC datagrams](https://www.rfc-editor.org/rfc/rfc9221.html) · [Game packet limit](../../crates/sf-engine/src/netplay/protocol.rs)

Start with one low-cost US East server at a stable project hostname embedded in release builds. Use a test endpoint in automated tests. The first release covers ordinary home and carrier NATs with outbound UDP available. Validate the relay certificate, use random expiring codes, cap rooms, participants, traffic, and queues, and rate-limit create and join attempts. Keep room state ephemeral. Monitor availability, packet rates and room counts. Keep diagnostic logs free of invite codes and gameplay payloads. Measure traffic and headroom on the proposed server before choosing the launch capacity. The release runbook covers deployment, DNS and TLS renewal, capacity, rollback, and what players see during outages. Name the operator responsible for the default service before enabling it in a stable release.

Publish the relay implementation and a documented Linux deployment from tagged source. Provide an example configuration and service setup with the public UDP listener, DNS, a client-trusted TLS certificate, renewal, health checks, and resource limits. The same server protocol works for the default relay and independently operated relays. A self-hosted relay has its own room codes and runs without contacting the default relay. The operator makes the relay's listener reachable. Players still use outbound connections from their own networks.

Preserve Wired Only and use each client's actual routed link for Ethernet or Wi-Fi telemetry. Add macOS route and media detection for the direct path. For Internet rooms, an unavailable link classification must not stop an ordinary connection or be shown as Ethernet. A Wired Only room requires verified Ethernet. Keep the actual remote link and the relay path conceptually distinct in diagnostics.

## Native packages

Use the same annotated version tag and Git revision for Windows x86_64, macOS, and Linux x86_64. Steam Deck uses the native Linux build. Keep the default tracker feature and ship the same approved art and voice packs, shaders, build identity, and dependency notices. The user supplies the same supported ROM set. Publish one archive and SHA-256 sidecar per platform under the same GitHub Release. Run the existing Windows package checks and extend equivalent checks to the other packages. [Current release guide](../../tools/release/README.md)

| Platform | Proposed first release |
| --- | --- |
| Windows | Keep the x86_64 ZIP and Windows install path. |
| macOS | Apple-silicon `.app` in a ZIP as a clearly labeled preview. Apply and verify an ad hoc signature after assembling the bundle. Use Metal, read bundled resources from the app bundle, and keep user data in the user's Library. Tell testers that the download lacks Developer ID and notarization. When Gatekeeper permits a per-app exception, point testers to Apple's first-launch instructions. |
| Linux desktop | Native x86_64 archive with a launcher and a documented distribution baseline. Build against the oldest supported runtime and verify on a clean system. Use per-user settings and data directories. |
| Steam Deck | Same Linux archive on stock SteamOS. Add the launcher as a non-Steam game in Desktop Mode, then launch and play in Gaming Mode with the built-in controls. Provide instructions for first-time ROM selection or placement. |

Choose minimum macOS and Linux versions and list the versions actually exercised. All platforms need to locate shaders and bundled packs independently of the launch directory, accept a user-supplied ROM through a documented first-run path, and keep local settings and saves across package updates. The Mac preview can ship with the matched release artifacts after the CI checks below. Label its desktop status explicitly until a volunteer tests the downloaded package on Apple silicon. Developer ID signing and notarization for ordinary Gatekeeper acceptance can follow when the project has credentials. Windows, Linux, and Steam Deck can reach stable acceptance on their own. ## Release acceptance

1. On each target, build from the same tagged source, verify architecture, exact `--version` and revision, package contents and dependency inventory, and run the extracted package's available smoke checks. Download the published archives and sidecars and verify the bytes against the checked build artifacts. On desktop Linux and Deck, verify the documented install on clean systems with standard user permissions. On a hosted Apple-silicon runner, verify the Mac bundle, ad hoc signature, minimum target, extracted CLI, deterministic simulation and automated relay tests. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
2. Compare confirmed simulation checksums for the same seeded fight and inputs across OS and CPU targets. Exercise the relay with multiple clients, including traffic loss, distinct guest and spectator routes, expiry, invalid and stale codes, room limits, disconnects, service outage, and two isolated rooms. Deploy a second relay using the community instructions. Confirm the unmodified release clients can select it, host and join by code, play, and switch back to the default. Check that a code from one relay is not routed to the other. Run the existing LAN and direct regression suites and check LAN play on a mixed-OS pair.
3. With actual packaged builds and the public endpoint, use two separately routed networks with no forwarded ports. Test each pair of Windows, Linux desktop, and Steam Deck with hosting in both directions. Join by code, finish a Versus match, and rematch. Also finish a cross-platform Dramatic Battle and exercise a mid-match spectator join. Include an outbound-only or carrier NAT path in the verification and record observed peer latency and rollback behavior. Use matching local ROM/data and art for the success case and verify the existing mismatch feedback in a separate run.
4. Verify that a Deck player can launch in Gaming Mode, read the menu at 1280×800, host, enter a code, fight, and rematch with its built-in controls. Check video pacing and audio. When a Mac tester is available, verify launch from a browser download through Finder, Metal rendering and the included looks, audio and controller input, and the same full-match acceptance with Mac in both host and guest roles. Record which platform pairings, OS versions, hardware, and network conditions were actually exercised.

## Builder decisions

Choose the relay and client libraries, control message encoding, packet envelope, code alphabet and expiry, and operational limits once the room lifetime and abuse cases are tested. Select native APIs and packaging tools that satisfy the release checks. Choose the Linux runtime baseline and confirm it against SteamOS and a supported desktop distribution. Choose the default hosting plan with the operator based on a low recurring cost, included bandwidth, and the measured capacity needed at launch.
